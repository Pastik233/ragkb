# 事务与隔离级别的细节

## 传播行为的实际影响

REQUIRED 会加入当前事务，内外层共享同一个物理事务，任何一处抛异常整个事务回滚。REQUIRES_NEW 会挂起外层事务，用新连接开一个独立事务，外层回滚不影响它，但它提交后外层再回滚也不会撤销。挂起的代价是占用两个数据库连接，嵌套层数多时容易把连接池耗尽。

NESTED 用保存点实现，只有一个物理事务，内层失败可以只回滚到保存点。它依赖 JDBC 的 Savepoint 支持，JTA 环境下不成立。

## 自调用为什么会失效

事务是基于代理实现的，代理对象在方法调用前后开启和提交事务。同一个类里用 this 调用另一个方法，走的是原始对象，不经过代理，注解完全不生效。这是排查“事务没回滚”时第一个要确认的点。

解决办法有三种：把方法拆到另一个 Bean；注入自己的代理然后通过代理调用；开启 exposeProxy 后用 AopContext.currentProxy 获取当前代理。

## 回滚规则

默认只对 RuntimeException 和 Error 回滚，受检异常不会触发回滚。要覆盖受检异常必须显式写 rollbackFor。另一个容易忽略的点是：异常被 catch 住没有抛出，事务管理器认为方法正常返回，会提交而不是回滚。如果必须捕获，要手动 setRollbackOnly。

## 隔离级别与只读事务

MySQL 默认是可重复读，靠 MVCC 提供快照。读已提交每次查询都新建快照，能看到别人已提交的数据。只读事务加上 readOnly 提示可以让数据库做优化，避免不必要的锁，但要注意它不能防止其他事务修改数据。
