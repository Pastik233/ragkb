# 分布式锁的几种实现

## Redis 方案

加锁用一条命令完成：SET key value NX PX 30000。NX 保证只有 key 不存在时才设置成功，PX 设置毫秒级过期时间。这两个必须放在同一条命令里，分成两条会出现“设置成功但没来得及设过期”的窗口。

value 要放一个唯一标识，比如 UUID，代表锁的持有者。解锁时不能直接 DEL，必须先比对 value 再删除，而且这两步要用 Lua 脚本保证原子性，否则可能出现“判断是自己的锁，删除前锁过期被别人拿走，结果删了别人的锁”。

过期时间怎么定是个难题。定短了业务没跑完锁就释放，定长了故障时锁迟迟不释放。主流做法是加看门狗：后台线程每隔一段时间检查业务是否还在执行，是就续期。Redisson 的实现是每 10 秒续期一次，默认锁 30 秒。

## RedLock 的争议

RedLock 的思路是向多个独立的 Redis 节点加锁，多数成功才算加锁成功。它的争议在于依赖时钟假设，在时钟漂移或者 GC 停顿的场景下安全性无法严格保证。Martin Kleppmann 和 antirez 有过一轮著名辩论，结论是：如果只是追求效率而非绝对正确，单节点加过期时间就够用；如果要求强一致，应该用带 fencing token 的方案。

## ZooKeeper 方案

ZooKeeper 靠临时顺序节点实现：每个客户端在锁节点下创建临时顺序节点，序号最小的持有锁，其他人监听前一个节点。会话断开时临时节点自动删除，天然避免了死锁。

缺点是性能不如 Redis，每次加锁释放都涉及集群写。etcd 用 lease 加 revision 也能实现类似效果。
