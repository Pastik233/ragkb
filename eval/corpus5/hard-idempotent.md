# 接口幂等的实现方式

幂等指同一操作执行多次和执行一次的效果相同。查询天然幂等，新增和支付类操作需要额外设计。

唯一键方案最直接：给业务单据加唯一索引，重复插入会抛冲突异常，捕获后返回已有结果。适合创建类接口，缺点是依赖数据库，且冲突异常的处理要小心事务状态。

状态机方案适合有明确生命周期的业务：订单只能从待支付流转到已支付，重复回调时判断当前状态，已经是目标状态就直接返回成功。它比唯一键更灵活，但要保证状态判断和更新是原子的，通常用带条件的 update。

Token 方案用于防止重复提交：进入页面时先申请一个 token 存进 Redis，提交时带上 token，服务端用 Lua 原子地删除并判断，删除成功才处理。这样同一个 token 只能用一次。

乐观锁用版本号：更新时带上 version 条件，影响行数为 0 说明已被别人改过。它解决的是并发覆盖，不是重复提交，两者常被混淆。

工程上还要考虑消息队列的重复消费。Kafka 至少一次投递意味着消费端必须幂等，常见做法是用业务唯一键落库去重表，或者把消费记录和业务数据放在同一个事务里。
